     Plan: Edit Mode Toggle in Top App Bar

     Context

     The edit/view toggle for "my own" recipes needs to live in the
     AddUpdateRecipeTopAppBar (in MainView.kt), not as a FAB inside the recipe
     screen. The button should be bidirectional: tap once to enter edit mode,
     tap again to return to view mode.

     The complication: AddUpdateRecipeTopAppBar is rendered in MainView outside
     the nav graph, so it has no direct access to AddEditRecipeViewModel.
     Solution: bridge through MainViewModel, which is already passed to the top
     bar.

     AddEditRecipeViewModel.isEditing (added in a prior step) will be removed
     and replaced by MainViewModel.isEditingRecipe as the single source of
     truth.

  Problem: If the user opens a recipe, enters edit mode, makes changes

  BackHandler becomes disabled. A swipe-back or hardware back press then pops
  the screen immediately with no warning. The top app bar back arrow still
  checks changesMade so it would show the dialog, but the system gesture would
  not.

  Fix: Change to BackHandler(enabled = isEditing || changesMade) so the
  unsaved-changes guard stays active even after toggling back to view mode.

  ---
  2. Critical — collectAsState() called inside a conditional branch

  Where: MainView.kt:203

  Screen.AddUpdateRecipeScreen(context).route -> AddUpdateRecipeTopAppBar(
      ...

  Problem: collectAsState() is a composable function and must be called
  unconditionally (Compose's Rules of Composables). When the route changes away
  from AddUpdateRecipeScreen and then back, this creates a new collectAsState()
  call at a different position in the composition tree, which can cause a
  runtime crash or silent misbehavior.

  Fix: Hoist the collectAsState() call to the top of MainView():
  val isEditingRecipe by mainViewModel.isEditingRecipe.collectAsState()
  Then pass isEditingRecipe directly to the call site.

  ---
  3. One-frame flash — new recipe opens briefly in view mode

  Where: Navigation.kt:278

  LaunchedEffect(id) { mainViewModel.setRecipeEditMode(id == 0L) }

  Problem: LaunchedEffect is asynchronous — it runs after the first frame is
  committed. On first composition, isEditingRecipe is still false

  technically one frame where the view-only layout is rendered before edit mode
  activates.

  shows the spinner, not the content. But it is worth verifying in a debug build
   with slow device mode enabled.

  ---
  4. View mode displayed with stale unsaved changes — UX risk

  Scenario: User opens recipe → edits title/ingredients → taps toggle icon →
  returns to view mode without saving.

  The view-only layout reads directly from addEditRecipeViewModel.recipeName,
  recipeIngredients, etc., so it will render the unsaved state of the recipe.
  This is internally consistent but could confuse the user who doesn't realise
  the view mode is showing uncommitted edits. There is no visual indicator (e.g.
   a "Unsaved" banner) in view mode.

  ---
  5. mainViewModel.setChangesMade(false) runs on every recomposition

  Where: Navigation.kt:280
